How the Enjaz assistant works today

A walk through everything that has actually been built — the infrastructure it runs on, the database underneath it, the pipeline that turns 58 project documents into 678 searchable passages in nine sealed compartments, the gate that decides who may open which project, the assistant a person actually types into, and the measurement that says whether any of it is any good.

Every number above was read from the running system, not from a document — docker compose ps, apply_migrations.py --status, pytest (620 Python + 25 JavaScript), pipeline.status (exit 0, HEALTHY) and pipeline.scanner --dry-run (rows written 0).

01

The whole machine, in one picture

Project documents sit in folders on disk. The system's job is to read every one of them, understand what is inside, and store it in a form a computer can search by meaning rather than by keyword — without ever mixing one project's documents with another's, and without ever paying twice to read the same file.

Four stages do that work, in a fixed order. Each one only does the work the one before it left behind, so any stage can be run again safely — on a corpus that has not changed, running the whole thing again does nothing at all and costs nothing.

The idea the whole design turns on

Reading a page through Azure costs about one cent, and the corpus is ~154 pages. That is small — but a pipeline that re-reads everything each time it runs would burn that repeatedly and, worse, hide the fact that nothing changed. So every stage asks a question first: is there already a result for this exact file? If yes, it does nothing.

02

Where it all runs

Everything lives in Docker containers on one PC. Thirteen are running right now. Eleven are infrastructure — databases and monitoring tools that came first — and two are the pipeline itself, the only application code that exists.

One hard rule shaped this: nothing Docker-related touches the C: drive. Docker's own engine disk was moved to D:\MOF_Installations\docker-data, and every container's data is bind-mounted to a plain, browsable folder under D:\MOF_Installations\volumes\.

mof-postgres-spmThe project database — projects, users, assignments, documents, and the cached OCR text.

03

What the database holds, and who is allowed to see it

Five tables, built up through thirteen numbered migration files that are applied by a script — never by hand. The script runs each file inside a single transaction, records it only after it succeeds, and stores a checksum so that editing an already-applied file is caught rather than silently accepted.

The most important table is the smallest. project_assignments is the list of which person may see which project. A project with no row there is invisible to everyone — not because code checks for it, but because there is nothing to find.

Both behaviours were tested rather than assumed: a plain UPDATE as spm_app returns permission denied, and a session that forgets to declare its project sees zero rows instead of all 58.

One deliberate exception exists, and it is narrow. Before a session is opened there is no current project, so the rules above would show a person nothing at all — including the names of their own projects, which is what a project chooser needs. A second rule lets someone read the entries for projects they are personally assigned to, and nothing more. Documents stay invisible until a project is actually chosen.

04

Stage 0 — finding out what is there

The scanner walks every project folder, reads each file, and calculates a SHA-256 fingerprint of its contents. Then it compares that fingerprint against what the database already knows, and takes one of five decisions.

It deliberately never reads the manifest that generated the mock data. The filesystem is the only source of truth — which is what makes dropping a new file into a folder enough to get it picked up, with no code change.

Two details worth knowing

  • Paths are stored relative — PRJ-01/charter.docx, not D:\MOF_DataSample\PRJ-01\charter.docx. The Windows PC and the Linux container mount the same folder at different places, and storing the full path made each of them rewrite all 58 rows every time the other one ran.
  • A row whose file has vanished is reported, never deleted. If the folder setting were ever pointed one level too high, every project would look empty — and deleting on that signal would take the paid-for extracted text with it.
05

Stage 1 — reading the documents

Each document is sent to Azure Document Intelligence, which returns its contents as markdown — headings, paragraphs, tables and reading order, rather than a flat wall of text. This is the step that costs money, billed by the page.

Every format goes through it, including Word and PowerPoint files whose text could technically be read for free. That was measured across 11 files rather than assumed, and the measurement reversed the original plan: reading a PDF's text directly returned Arabic as scrambled display glyphs (36 usable characters against Azure's 2,623), Word files duplicated merged table cells, and a Word document is billed as a single page no matter how long it is. The saving was imaginary; the damage was not.

A judgement call built into the code

A scanned document whose content lives inside images comes back nearly empty. That is flagged for a human, not marked failed — because a file like that can never improve, and marking it failed would re-bill it on every future run forever.

06

Cutting documents into searchable passages

A whole document is too big to search meaningfully — ask about one risk and you would get back a page containing twelve. So each document is cut into passages of roughly 600 words' worth of tokens. How to cut is the interesting part, and the design was corrected three times by real documents disagreeing with the plan.

Three assumptions turned out to be wrong: tables come back as HTML rather than tidy markdown tables; two of the first four documents had no headings at all, because whoever wrote them used bold text instead of real heading styles; and keeping a big table whole produced one 3,331-token block in which any single row was drowned out.

07

Stages 2 and 3 — turning passages into searchable vectors

Each passage is sent to an Azure embedding model, which returns a list of 1,536 numbers describing its meaning. Passages about similar things end up with similar numbers, which is what lets a question in Arabic find an answer written in different words.

Chunking and embedding were built as one step rather than two, for a blunt reason: chunking is free, embedding is paid. A boundary between them would end with hundreds of paid-for vectors held in memory that nothing had saved yet. An embedding that is not stored is money thrown away, so the paid call and the durable write live in the same per-document transaction.

The isolation was not taken on trust. Every one of the 678 stored payloads was read back and checked against the collection it sits in: zero cross-project contamination.

08

How it runs itself

For most of the build, the three stages were commands a person typed. That is fine for building them and useless for operating them — dropping a file into a folder did nothing until someone remembered to run the scanner. Now a scheduler fires one full ingest a day, and dropping a file in is the entire procedure.

The timezone is part of the schedule, not decoration. Containers run on UTC, so asking for 13:00 without naming the zone would have fired the job at 16:00 local time.

09

Knowing whether it is healthy

One command answers the three questions an operator actually asks: when did this last work, is anything broken, and do the two stores still agree with each other? It exits 0 for healthy and 1 for needs-attention, so it works as an automated check without anyone reading its output.

That third question is the one nothing else in the system can answer. The database row and the vectors are written for each document together, but they live in two separate systems — and there is a moment between the two writes.

10

Who is allowed to see what

The strictest requirement in the whole brief is that no one may see documents from a project they are not assigned to — under any circumstance. Three separate mechanisms stand behind it, and only one of them is ordinary application code.

That one matters most, because it is the only one that can be forgotten. It was built after being shown to be necessary: a user assigned to three projects, opening a session on a fourth, was handed that fourth project's data without complaint. Not a bug — the database faithfully serves whatever project the session claims to be about. Deciding whether that claim is allowed is a separate job, and nothing was doing it.

What the assistant can never do

  • Write anything. The application's database account has read permission only. "The assistant makes no changes to any system" stopped being a promise and became something the database enforces.
  • Run with the pipeline's privileges. The pipeline's account can reach every project — it has to, to process them all. If the application were ever configured with that account by mistake, it refuses to start rather than quietly seeing everything.
  • Treat an outage as permission. If the database cannot be reached, the answer is a refusal, never an empty result that looks like "nothing to see here".
One honest limitation

The gate decides whether a user may open a project. It does not verify that they are who they say they are — real staff sign-on is an external system that isn't available here. That deferral is deliberate and written down rather than disguised, and whatever supplies the identity later becomes part of this boundary.

11

Measuring whether search actually works

Until recently nobody could answer a simple question: did that change make search better? There were impressions — Arabic seemed weaker than English, the right passage often came second rather than first — and impressions are a poor basis for spending effort.

So there is now a set of 29 realistic questions, in Arabic, English and mixed, spanning all nine projects, each tagged with the document that genuinely contains the answer. Written by reading the extracted text, not by guessing from filenames. Running it costs a fraction of a penny.

The measured baseline

All2979%90%0.84

Mixed367%100%0.78

The "ranking score" is 1.00 when the right answer is always first and 0.50 when it is typically second. It leads the report rather than a simple hit rate, because the known weakness is ordering: a hit rate can stay flat at 90% while the answer moves from third place to first, which is a large real improvement that a hit rate cannot see.

The measurement immediately corrected a belief

Arabic was assumed to rank worse than English. It scores lower on raw similarity — but the ordering is almost identical, and Arabic actually does slightly better at finding the answer within the top five. A low similarity score is not the same thing as a bad rank, and the two had been quietly conflated. The obvious fix that belief implied would have been effort spent on a problem that isn't there.

The question set is checked against the live document list before anything runs. If a document is renamed, the check fails loudly — because a question pointing at a document that no longer exists would score zero forever and look exactly like search getting worse.

12

What happens when someone types a question

Everything up to here builds and guards the knowledge base. This is the part a person actually touches: a sign-in page, a project to choose, and a box to type into. One question travels through nine steps, and the interesting thing about them is how few decisions the code makes.

Three rules that shape the whole path

  • The browser never says who it is. It sends the question and nothing else. Identity is established by the server from a signed cookie that JavaScript on the page cannot read — which was confirmed by trying to delete it from the page and failing.
  • Everything the server returns is inserted as text. Document content is not trusted input. The same reasoning that fences untrusted text out of the prompt fences it out of the page, and a test checks the whole file for any place that could break the rule.
  • Every refusal is decided on the server. The page renders decisions; it never makes them. It cannot decide to show a project, to answer without evidence, or to soften a refusal, because it is never given the choice.

Four locks, not one

A question can only ever reach one project's material, and four independent things have to fail before that stops being true: the sign-in gate, the database's own row-level rules, the fact that each project's vectors live in a physically separate collection, and the fact that the collection name is derived from the checked session rather than from anything the caller sent. No single mistake opens two projects.

13

The system prompt is the brain

There was once a rule-based router: a language detector, a phrase list, a table of intents. It was accurate, it was fast, and it was deleted. The requirement was that every input goes to the model and nothing is hard-coded — so the routing moved into the prompt, and the code that used to decide was removed rather than left switched off.

What moved, and where it went
DecisionBeforeNow
What language is this?Script counting, plus a statistical identifier for Latin textThe model, in the same call that answers
Is this a greeting, an overview request, a lookup?An exact-match phrase list held as dataThe model, in the same call
Is this language supported at all?A configured list of codesThe model, which apologises in the language it was asked in
Is there enough evidence to answer?Still the code: below a measured similarity floor the model is not called at all, and the honest refusal costs nothing

The trade was made with open eyes. One call instead of two is faster, and it removes an entire class of bug where the router and the answer disagreed with each other. What it costs is determinism: a rule either fires or it doesn't, while a model is asked to be consistent. That is why the router is now measured rather than assumed.

How something non-deterministic is held to account

59 tagged probes are pushed through the real path — a real session, a real project, the real prompt — and the language and intent it chose are scored against what they should have been. Language lands at 96.6–98.3%, intent at 96.6%.

That first figure is a range, not a number, and the range is the honest part: two consecutive runs at temperature zero did not agree. Recording a single value would have implied a stability the system does not have. The floor is what any change must beat.

The evaluation corrected the author, not the model

On its first full run the harness reported failures that turned out to be three probes tagged wrong by hand. The model had been right and the expectation was wrong. That is the argument for measuring against a written-down answer key rather than reading transcripts and forming an impression — an impression would have quietly agreed with whoever wrote it.

What the prompt is not allowed to do

  • It may not answer from its own knowledge. The evidence supplied with the question is the only permitted source of fact. Absent evidence, the required output is an apology, not a plausible sentence.
  • It may not cite what it was not given. Citations are resolved against the passages actually retrieved, so a fabricated source has nothing to resolve to.
  • It may not answer about another project. By the time the prompt is built, the material from any other project is not merely filtered out — it was never fetched.
14

Remembering the conversation

“And the end date?” is a perfectly normal thing to ask second, and a meaningless thing to search for on its own. Follow-ups are what make a chat a chat, and they are also where a retrieval system quietly falls over.

When a follow-up retrieves nothing above the evidence floor, the question is rewritten against the conversation so far — carrying its subject with it — and searched once more. Once, not repeatedly: a second failure is an honest “not in the documents”, and a retry loop against a five-second budget would turn a clean refusal into a timeout.

Conversations live in Redis rather than in the server's memory. That is what lets the API be restarted, or run as more than one worker, without a person losing the thread mid-sentence — verified by restarting the process under a live conversation and watching a bare Arabic follow-up still resolve correctly.

A stored project code is a claim, not a permission

A conversation read back from Redis says which project it belongs to. It would be easy — and wrong — to treat that as authorisation, because it was written when the chat opened and the world has moved on since: assignments change, and people leave. Every read re-runs the gate from scratch. If the answer is now no, the conversation is simply not there.

History is bounded twice over, by turns and by tokens. Turns are what a follow-up plausibly refers back to; tokens are what the latency budget can afford. Neither bound alone is enough — six short turns and six long ones are very different amounts of prompt.

15

Watching it work

Two observability systems were already running, for two genuinely different audiences: Grafana for engineers asking why something was slow, Langfuse for anyone asking what the model was actually sent. The temptation was to instrument twice. That was refused.

One instrumentation, two backends. The code records a span once; it is exported to both. Two SDKs would mean two sets of instrumentation calls placed by hand in the same functions, and they drift — one gets a new span, the other doesn't, and the two pictures of the same request stop agreeing.

The same chat turn, in both systems
SpanTypicalWhat it tells you
POST /api/conversations/{token}/messages2808 msThe whole request. Recorded against the route template, so a thousand conversations group into one line instead of a thousand
  chat.turn2790 msThe answering work, minus HTTP overhead
    retrieval.embed590 msTurning the question into a vector — a network call, and it shows
    retrieval.search17 msThe vector search itself. Never the bottleneck
    spm.fetch2 msThe live project record
    chat gpt-5.4-mini2045 msThe model. Three quarters of the time, which is where any latency work has to start

The shape of that trace is itself the answer to “why does it take three seconds?”. Searching is free; the two network calls to Azure are the entire cost. No amount of tuning the search will move it.

Tracing fails open — and that is the one place it is allowed

If a tracing backend is down, unreachable, or misconfigured, the request still succeeds. An observability outage must never become a service outage, and a person asking about their project should not be told no because a dashboard is unwell. Every rule about access fails the opposite way: when in doubt, refuse. The rate limiter is the only other thing here that fails open, and for the same reason — it guards a budget, not a boundary.

One thing is deliberately never recorded: a failed sign-in does not log the address that was tried. A log of attempted addresses is a list of who might exist, sitting in a system that is easier to read than the one it describes.

16

How any of this is known to work

645 automated tests, running in about twenty seconds. But the tests are not the interesting part — the method used to check the tests themselves is.

Every safety feature was proved by deliberately breaking it and confirming that the intended test caught the break. 74 such breakages were run across the pipeline and the access gate, and everything added since has been held to the same standard — the frontend, for instance, was checked against twelve, all caught. The ones that slip through are the valuable ones: each has exposed a real gap that was invisible on inspection, including a test that quietly passed against broken code because it imported the very constant it was supposed to be checking, and a security check that no test was watching at all.

One of those twelve is worth repeating, because the fault was in the test rather than the code. A test asserting that the model's chosen language beats guessing from the alphabet passed even with that logic torn out — it used a plain English sentence, which guessing also gets right. Rewritten to use an English answer that names an Arabic project, where the two genuinely disagree, it caught the break immediately. A test that cannot fail is not a test, and only breaking it on purpose tells you which kind you have.

What the tests deliberately do not fake

  • The database is real. Tests run against the actual schema and constraints inside a transaction they always roll back, so nothing survives the run. If the container is down they skip with a clear message rather than failing obscurely.
  • The lock is real. Set-if-absent, expiry and compare-and-delete are precisely the properties a fake dictionary would not have.
  • The paid services are stubbed. Both money-spending stages are fully tested — including their failure paths — without a single billed call and without touching the live vector store.
The lesson that keeps repeating

The worst defects here were invisible to a passing test suite and only appeared when something was actually run: a connection that closed itself, character positions wrong on 8 of 10 passages, a stored path that only broke once a second machine mounted the same folder elsewhere, and a connection pool that was quietly throwing away every connection it was given.

The most expensive lesson, kept on the record

The tests that check the assistant cannot write to the database used real delete statements, and relied on the database account's lack of permission to stop them. During a deliberate break — where that account was swapped for the powerful one, precisely to prove the tests would notice — the deletes succeeded and were saved before the test could report the problem. It destroyed the document records and the paid-for extracted text.

Everything was rebuilt from source files and version control, and the extraction re-run for about $1.54. The rebuild came back identical: same passage counts per project, same token totals. The fix is a general one worth stating plainly — a test that does something destructive must not rely on the thing it is testing to keep it safe. Those tests now undo their own work no matter what happens, and the break-testing tool takes a database snapshot and checks the corpus after every single break.

The code that exists

Four separate packages, each with one job — and the last of them is now something a person can type into.

What each package is for
PackageJobDatabase account
pipeline/Builds the knowledge base — discovery, extraction, chunking, indexing, plus the worker, scheduler, locks and health checkthe powerful one: it must reach every project
evaluation/Judges it — the tagged question set, the scoring, and the recorded baselineread-only, all projects
Application/Serves it — the access gate, the scoped data layer, the system prompt, the HTTP API and the single-file web interfacethe restricted one: read-only, one project at a time
observability/Watches it — one instrumentation, exported to both Grafana and Langfusenone: it holds no data of its own

The separation is not filing tidiness. The three run as different processes with deliberately different privileges, and the one that faces users has the least. A module in Application/ reaching for the pipeline's database account is a module doing something wrong, and the code refuses to start if it happens.

One rule holds all of it together: every setting is read from a single configuration file — no path, endpoint or project code is written into the code itself. That is why the pipeline could move into a container without a single code change, and why pointing this at a real document library later is configuration rather than a rewrite.
